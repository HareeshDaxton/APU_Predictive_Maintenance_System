================================================================================
  PHASE 5 — MONITORING AND DRIFT DETECTION
  Status: NOT DONE — code written now, activates after deployment
================================================================================

WHAT THIS PHASE IS:
  Monitor the model's health in production. Detect when sensor data
  patterns start drifting away from what the model was trained on.
  Alert Hareesh when the model starts degrading.

  CRITICAL NOTE ON DRIFT DETECTION METHOD:
  This project uses TIME-SERIES sensor data (engine cycle sequences).
  Standard drift detection methods (like population stability index or
  simple column-level KS tests) are designed for IID (independent and
  identically distributed) data — they do NOT account for temporal
  autocorrelation in time series.

  For time-series industrial sensor data, the industry-standard approach is:

  METHOD 1 — ROLLING WINDOW STATISTICS (what we implement):
    Compare the rolling mean and rolling std of each sensor over the
    last N cycles against the training baseline statistics.
    This is the simplest and most interpretable method for maintenance.
    Threshold: if rolling_mean deviates > 2 std from training baseline,
    flag as drifted.

  METHOD 2 — ADWIN (Adaptive Windowing) — future enhancement:
    ADWIN is designed specifically for streaming/time-series data.
    It maintains a sliding window and automatically detects when the
    statistical distribution of sensor readings changes.
    Library: river (pip install river)
    from river import drift
    detector = drift.ADWIN()
    — Use this when you need more sensitive drift detection later.

  METHOD 3 — PAGE-HINKLEY TEST — future enhancement:
    Designed for sequential/streaming data, detects gradual mean shifts.
    Better than KS test for time-series because it respects temporal order.
    Available in: river library and scikit-multiflow.

  METHOD 4 — EVIDENTLY AI (what we add to retrain pipeline):
    Evidently AI is an open-source library that generates full HTML
    drift reports. It supports time-series-aware drift detection.
    Install: pip install evidently
    Use in retrain.py before training to generate a drift report:
    from evidently.report import Report
    from evidently.metric_preset import DataDriftPreset
    report = Report(metrics=[DataDriftPreset()])
    report.run(reference_data=train_df, current_data=new_data_df)
    report.save_html("drift_report.html")
    Upload drift_report.html to GCS for Hareesh to review.

  FOR THIS PROJECT, WE IMPLEMENT METHOD 1 NOW AND NOTE METHOD 4
  AS THE UPGRADE PATH.

  6. If drift_detected is True, log a WARNING message

  Because this is engine cycle time-series data, do not just compare
  raw sensor values. Compare the ROLLING MEAN of each sensor
  (computed over the last 20 cycles of each engine in the uploaded file)

  more accurately than a single-value comparison.

WHAT TO BUILD:
  Create file: src/monitoring/prediction_drift.py

  This module queries Cloud SQL to detect if predicted RUL values
  are shifting over time.

  def check_prediction_drift():
      Query last 4 weeks of predictions from Cloud SQL:
        SELECT DATE_TRUNC('week', timestamp) as week,
               PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY predicted_rul) as median_rul
        FROM predictions
        WHERE timestamp > NOW() - INTERVAL '4 weeks'
        GROUP BY week
        ORDER BY week;

      Compute rolling 4-week average of median_rul
      If current week median_rul < (4_week_avg * 0.80):
          Return {"prediction_drift": True,
                  "current_median": ...,
                  "4_week_avg": ...,
                  "drop_pct": ...}
      Else:
          Return {"prediction_drift": False}

  Call this function in retrain.py before deciding whether to retrain.
  If prediction drift is detected, always retrain regardless of schedule.

    def log_custom_metric(metric_name, value, project_id):
        client = monitoring_v3.MetricServiceClient()
        project_name = f"projects/{project_id}"
        series = monitoring_v3.TimeSeries()
        series.metric.type = f"custom.googleapis.com/apu/{metric_name}"
        point = monitoring_v3.Point()
        point.value.double_value = value
        now = time.time()
        point.interval.end_time.seconds = int(now)
        series.points = [point]
        client.create_time_series(
            request={"name": project_name, "time_series": [series]}
        )
