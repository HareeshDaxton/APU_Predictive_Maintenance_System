================================================================================
  SPEAKER 1 — LAKCHANA
  TOPIC: Introduction & Problem Background
================================================================================

What to say:

  1. Open the presentation. Welcome the audience.

  2. Introduce the project:
     "Our project is called the APU Predictive Maintenance System.
      APU stands for Auxiliary Power Unit — it is a small but critical engine
      in aircraft that provides power when the main engine is off."

  3. Explain the problem:
     "Traditional maintenance is either scheduled (we change parts on a fixed
      schedule, wasting good parts) or reactive (we fix it after it breaks —
      which is dangerous). Predictive Maintenance solves this by using
      sensor data to predict WHEN the engine is going to fail — before it
      actually does."

  4. State the project goal clearly:
     "Our goal is to predict the Remaining Useful Life — or RUL — of an APU
      engine. RUL tells us: how many more operational cycles does this engine
      have before it fails? This gives the maintenance team time to act."

  5. Introduce the dataset:
     "We used the NASA CMAPSS dataset — a real aerospace simulation dataset
      containing sensor readings from 260 aircraft engines over thousands of
      operational cycles. Each row is one cycle of one engine, with 21 sensor
      readings and 3 operational settings."

  6. Hand over to Farhana:
     "Now Farhana will walk you through how we prepared and enriched this data."

================================================================================
  SPEAKER 2 — FARHANA
  TOPIC: Data Preparation — Fault Injection & Feature Engineering
================================================================================

What to say:

  1. Fault Injection:
     "The NASA dataset only contains healthy engine data — there are no fault
      labels. So we used a technique called Fault Injection to synthetically
      create 5 different fault patterns in the data."

     "We used an Isolation Forest — an unsupervised machine learning model —
      to score how anomalous each data point is. Then we injected 5 types of
      faults: gradual sensor drift, sudden bias shifts, increasing noise, random
      spikes, and coupled sensor faults — each affecting different sensors."

     "This expanded our dataset to 6 times the original size, giving the model
      a much richer set of degradation patterns to learn from."

  2. Data Splitting:
     "We split the data into 80% training and 20% testing — but critically,
      we split by ENGINE, not by individual rows. This prevents data leakage —
      the model never trains and tests on the same engine's cycles."

  3. Feature Engineering:
     "We then engineered 4 key types of features from the raw sensor data:

      First — the RUL label itself: remaining cycles = max cycle minus current cycle.
      This is what the model learns to predict.

      Second — operating condition normalization: sensors are mean-centered
      within each flight condition so the model focuses on degradation,
      not on flight mode differences.

      Third — cycle normalization: we convert cycle number to a 0-to-1 scale
      representing the percentage of engine life consumed.

      Fourth — rolling window features: for each sensor, we compute the
      rolling average, rolling standard deviation, and trend over the
      last 5 cycles. This gives the model temporal context — is the
      sensor stable or deteriorating?"

  4. Hand over to Hareesh:
     "Now Hareesh, who built the entire system, will explain the model and
      show you a live demonstration."

================================================================================
  SPEAKER 3 — HAREESH
  TOPIC: Model Training + Inference Pipeline + Live Demo
  (Main Developer — most technical section)
================================================================================

What to say:

  1. Model Selection:
     "For this regression task — predicting a continuous RUL value — I chose
      LightGBM, a gradient boosting framework by Microsoft. It is extremely
      fast, handles tabular sensor data very well, and is the industry standard
      for this type of structured time-series problem."

  2. Training setup:
     "The model was trained on 69 engineered features — including rolling
      statistics for 14 informative sensors, cycle normalization, operating
      condition normalization, and the anomaly score from our Isolation Forest.
      The target variable is RUL — the number of cycles remaining."

  3. Results:
     "After training, our model achieves:
       — MSE  : ~0.14  (very low mean squared error)
       — MAE  : ~0.30  (on average, off by less than one cycle)
       — RMSE : ~0.37
       — R²   : 0.99   (explains 99% of the variance in RUL — excellent fit)"

  4. Inference Pipeline:
     "I built a complete inference pipeline that takes any new, unseen CSV file
      of engine sensor data and runs the same preprocessing steps — condition
      normalization, rolling features, scaling — then predicts RUL for every
      single cycle in that file. The output is a combined report with per-cycle
      predictions AND per-engine accuracy metrics."

  5. LIVE DEMO (open the browser at http://127.0.0.1:5000):
     "Let me show you the frontend I built for this — we call it APUWATCH,
      styled as a flight management system dashboard."

     → Upload a CSV file
     → Click EXECUTE INFERENCE SEQUENCE
     → Show the processing screen
     → Show the dashboard: gauge rings (MSE/MAE/RMSE/R²), the RUL prediction
       chart (true vs predicted), and the cycle-level telemetry table with
       CRITICAL / WARNING / NOMINAL status badges

     "You can see the model tracks the true RUL almost perfectly in green,
      with the predicted RUL in amber dashed — an R² of 0.99 means our
      predictions are extremely close to reality."

  6. Hand over to Kavin:
     "Kavin will now wrap up with a summary and what this project could
      look like in the future."

  SPEAKER 4 — KAVIN
  TOPIC: System Architecture Overview + Conclusion + Future Work

What to say:

  1. System Architecture (brief overview):
     "Let me give you a quick picture of how all the pieces connect.
      The system has four layers:
        — Data Layer    : Raw NASA sensor data → fault injection → train/test split
        — ML Layer      : Feature engineering → LightGBM model → saved artifacts
        — Inference Layer: New CSV in → preprocessing → prediction → report out
        — Presentation Layer: A Flask web server with a full dashboard frontend
          where users upload data and see results visually."

  2. Why this matters:
     "From a software perspective, what makes this system production-ready is:
      — All configuration in one central config.yaml file
      — Custom logging and exception handling for every pipeline step
      — A clean entrypoint system so any pipeline can be run independently
      — A web interface that any maintenance engineer can use without
        needing to know Python or machine learning"

  3. Conclusion:
     "To summarize — we built a complete, end-to-end APU Predictive Maintenance
      system that takes raw engine sensor data and tells you exactly how many
      cycles that engine has left. The model achieves a 99% R² score, the
      interface is aviation-grade, and the pipeline is modular and extensible."

  4. Future Work:

        — Dockerizing the application for cloud deployment
        — Adding MLflow tracking to the training pipeline for better
