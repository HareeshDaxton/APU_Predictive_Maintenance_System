================================================================================
  SECTION 1: WHAT IS THIS PROJECT?
================================================================================

Full Name : APU Predictive Maintenance System
Goal      : Predict the Remaining Useful Life (RUL) of an Auxiliary Power Unit
            (APU) engine — i.e., how many more operational cycles it has before
            it fails — AND support detection of the fault type causing degradation.

Why APU?
  An Auxiliary Power Unit is a small engine on aircraft / vehicles that provides
  electrical power when the main engine is off. Predicting its failure cycle
  allows maintenance teams to act BEFORE breakdown (Predictive Maintenance vs.
  Reactive Maintenance). This saves costs and prevents dangerous in-flight
  failures.

What the system does end-to-end:
  1. Takes raw engine sensor time-series data (NASA CMAPSS format) as input.
  2. Synthetically injects 5 fault types into the healthy data to create a
     labeled training dataset.
  3. Splits data by engine (engine-based split) to prevent data leakage.
  4. Engineers features: RUL, op-condition normalization, cycle normalization,
     rolling statistics (window=5), StandardScaler.
  5. Trains a LightGBM Regressor to predict per-cycle RUL.
  6. Provides an Inference Pipeline that accepts NEW unseen CSV files and
     outputs per-cycle RUL predictions + validation metrics.
  7. Serves a professional Aviation-themed web frontend (Flask + Chart.js) for
     uploading CSV files, running inference, and viewing results interactively.

Model type: REGRESSION (predicts exact number of cycles remaining, not just
            a binary "will it fail" flag).


================================================================================
  SECTION 2: THE DATASET
================================================================================

Source Dataset:
  File   : Artifacts/raw/train_FD002.csv
  Origin : NASA CMAPSS (Commercial Modular Aero-Propulsion System Simulation)
           Dataset — specifically the FD002 subset.
  Size   : ~8.8 MB (thousands of engine cycles across 260 engines)

Raw dataset columns (each row = one operational cycle of one engine):
  - engine_id       : Unique engine ID (1 to 260)
  - cycle           : Cycle number (starts at 1, increases until engine fails)
  - op_setting_1/2/3: Three operational settings (altitude, load, etc.)
  - sensor_1 to sensor_21: 21 onboard sensor readings per cycle

This raw data contains ONLY HEALTHY engines. The engine degrades naturally
until the last cycle. There are NO fault labels in the raw data.


================================================================================
  SECTION 3: FAULT INJECTION
================================================================================

Script : NoteBook/Fault_injection/fault_injection.py
         (Production version: src/Data_preprocessing/Fault_injection/fault_injection.py)

Since the NASA dataset has no explicit fault events, we SYNTHETICALLY INJECT
faults. An Isolation Forest is first trained on the healthy data to score
anomalies. Then 5 fault patterns are applied independently to every engine.

5 Fault Types:
  -----------------------------------------------------------------------
  ID | Name            | Affected Sensors       | Pattern
  -----------------------------------------------------------------------
  0  | healthy         | none                   | Original data unchanged
  1  | gradual_drift   | sensor_2, sensor_7     | Values slowly drift ±10%
  2  | bias_shift      | sensor_4, sensor_8     | Sudden constant offset
  3  | noise_increase  | sensor_3               | Noise grows 1x→3x std
  4  | spike           | sensor_9               | Random spikes (3–5x std)
  5  | coupled_fault   | sensor_11, sensor_12   | Two sensors drift together
  -----------------------------------------------------------------------

Output: Artifacts/Fault_injected_data/Fault_injection_dataset.csv
  Adds columns: anomaly_score, fault_label, fault_type, fault_target
  Size   : 6× the raw data (260 engines × 6 variants = 1,560 engine histories)

Integrity checks run automatically:
  - Classes balanced (equal rows per fault type)
  - No NaN values
  - Healthy portion byte-identical to raw
  - Faulty anomaly scores higher than healthy


================================================================================
  SECTION 4: DATA SPLITTING
================================================================================

Script : entrypoint/data_split.py → src/Data_preprocessing/Data_split/Data_split.py

Input : Artifacts/Fault_injected_data/Fault_injection_dataset.csv
Output: Artifacts/Data_split/Train_datasets/train_dataset.csv
        Artifacts/Data_split/Test_datasets/test_dataset.csv

Split method: ENGINE-BASED (not row-by-row)
  - 80% of engines → train, 20% → test
  - Order within each engine (cycles) is preserved — NOT shuffled
  - Random seed = 42 for reproducibility
  - Prevents DATA LEAKAGE: model never trains on cycles from an engine it
    will be tested on (mirrors real-world deployment conditions)


================================================================================
  SECTION 5: FEATURE ENGINEERING
================================================================================

Script : entrypoint/feature_engineering.py
         → src/Pipelines/feature_engineering_pipeline.py (class: FeatureEngineering)

Input : train_dataset.csv + test_dataset.csv
Output: Artifacts/preprocessed/train_preprocessed/train_preprocessed.csv
        Artifacts/preprocessed/test_preprocessed/test_preprocessed.csv
        Artifacts/Scaler/scaler.pkl

Active sensors (14 informative sensors — 7 noisy ones dropped):
  sensor_2, sensor_3, sensor_4, sensor_7, sensor_8, sensor_9,
  sensor_11, sensor_12, sensor_13, sensor_14, sensor_15, sensor_17,
  sensor_20, sensor_21

Engineering steps:

  Step 1 — RUL:
    RUL = max_cycle_of_engine - current_cycle
    This is the regression TARGET variable.

  Step 2 — Operating Condition Normalization:
    Sensors are mean-centered within each (op_setting_1/2/3) group.
    Removes "operational bias" so model focuses on degradation, not flight mode.

  Step 3 — Cycle Normalization:
    cycle_normalized = cycle / max_cycle_of_engine  (range: 0 to 1)
    Represents % of engine life consumed.

  Step 4 — Rolling Window Features (window=5, min_periods=1):
    For each of 14 sensors: {sensor}_rolling_mean, {sensor}_rolling_std,
    {sensor}_trend (diff). Gives temporal context to the model.

  Step 5 — StandardScaler:
    All numeric features (except engine_id, RUL, fault cols) scaled to
    mean=0, std=1. Scaler is FIT on train only, then transform-applied to test.
    Saved as Artifacts/Scaler/scaler.pkl for use at inference time.

  IMPORTANT: anomaly_score IS INCLUDED as a model input feature (it was
  deliberately kept in X during training — do NOT drop it at inference).


================================================================================
  SECTION 6: MODEL TRAINING
================================================================================

Script : entrypoint/training.py → src/Pipelines/trainig_pipeline.py

Algorithm: LightGBM Regressor (LGBMRegressor)
  Fast gradient boosting framework. Builds an ensemble of decision trees
  that correct each other's errors. Excellent for tabular sensor data.

Hyperparameters (config/config.yaml):
  n_estimators     : 400
  learning_rate    : 0.05
  max_depth        : -1    (unlimited, controlled by num_leaves)
  num_leaves       : 50
  subsample        : 1.0
  colsample_bytree : 1.0
  min_child_samples: 20

Features (X): All engineered columns EXCEPT engine_id, fault_label,
              fault_type, fault_target, RUL
  NOTE: anomaly_score IS included in X (the model was trained with it).

Target (Y): RUL (continuous regression)

Metrics:
  MSE, MAE, RMSE, R² (R-squared)

Output: Artifacts/Model/model_LGBM.pkl (~1.8MB, saved with joblib)


================================================================================
  SECTION 7: INFERENCE PIPELINE  ← NEW (completed 2026-03-31)
================================================================================

Script : src/Pipelines/inference_pipeline.py (class: InferencePipeline)
CLI    : python -m entrypoint.inference --input path/to/file.csv

Purpose:
  Accepts any NEW, UNSEEN CSV file containing engine sensor data and outputs:
  1. Per-cycle predictions (engine_id, cycle, true_RUL, predicted_RUL)
  2. Per-engine metrics + OVERALL metrics (MSE, MAE, RMSE, R²)
  All saved as a single combined report file.

Input requirements (CSV):
  REQUIRED columns: engine_id, cycle, op_setting_1, op_setting_2, op_setting_3,
                    sensor_1 through sensor_21
  OPTIONAL columns: anomaly_score (auto-filled as 0.0 if absent), fault_label,
                    fault_type, fault_target (ignored if present)
  - Must be sorted by (engine_id, cycle) ascending
  - Supports ANY number of rows (dynamic size — 5 rows or 10,000 rows)
  - Supports ANY number of engines in the same file

Preprocessing steps (MUST mirror training exactly):
  1. Load and validate input CSV
  2. Compute proxy RUL: max_cycle_per_engine - current_cycle
  3. Normalize operating conditions (mean-center within op_setting groups)
  4. Add cycle_normalized = cycle / max_cycle_per_engine
  5. Add rolling features (window=5, min_periods=1) for 14 sensors
  6. Inject anomaly_score = 0.0 if the column is missing
     (The scaler was trained with anomaly_score; new clean data won't have it,
      so we default to 0 meaning "no anomaly detected")
  7. Apply saved StandardScaler (TRANSFORM ONLY — never refit on new data)
  8. Drop non-feature columns (engine_id, RUL, fault_label, fault_type,
     fault_target) — anomaly_score IS KEPT as a model feature
  9. Run model.predict(X) — 69 features expected by the model
  10. Compute metrics: MSE, MAE, RMSE, R²
  11. Save single combined report CSV

Output file: Artifacts/model_validations/report_TIMESTAMP.csv
  Structure:
    # -- SECTION 1: CYCLE-LEVEL PREDICTIONS --
    engine_id, cycle, true_RUL, predicted_RUL
    [all prediction rows]

    # -- SECTION 2: ENGINE METRICS --
    engine_id, num_cycles, MSE, MAE, RMSE, R2
    [per-engine rows]
    OVERALL, [total_rows], MSE, MAE, RMSE, R2

  NOTE: Previously two separate files (predictions_TIMESTAMP.csv and
  metrics_TIMESTAMP.csv) were generated. These have now been MERGED into one
  single report_TIMESTAMP.csv file.

Understanding true_RUL vs. predicted_RUL:
  - true_RUL: The PROXY ground-truth calculated from the input file itself
    (max_cycle - current_cycle). It tells you how many cycles remain within
    the time window present in the file.
  - predicted_RUL: What the LightGBM model predicts from the sensor readings.
  - For VALIDATION: feed the test dataset (full engine histories are known) →
    true_RUL is accurate → compute MSE/MAE/RMSE/R² meaningfully.
  - For PRODUCTION: true_RUL from a live feed is a RELATIVE proxy only (engine
    hasn't failed yet). You can validate later, once the engine actually fails,
    by comparing past predictions to the known end date.

Key bugs fixed during development:
  - Missing anomaly_score: scaler crashed → fixed by auto-injecting 0.0
  - Feature count mismatch (68 vs 69): anomaly_score was wrongly dropped from
    _select_features → fixed by keeping it in X (model was trained with it)
  - Windows charmap encoding error: → replaced Unicode arrows with ASCII ->
    and added sys.stdout.reconfigure(encoding='utf-8') in Flask app


================================================================================
  SECTION 8: VALIDATION STRATEGY
================================================================================

Two validation scenarios:

SCENARIO A — OFFLINE TESTING (known full engine histories):
  Use: Artifacts/Data_split/Test_datasets/test_dataset.csv
  This file contains complete engine histories (all cycles, start to failure).
  true_RUL is computed from the last cycle for each engine, which IS accurate.
  Run: python -m entrypoint.inference --input Artifacts/Data_split/Test_datasets/test_dataset.csv
  Output: Full metrics (MSE, MAE, RMSE, R²) with real ground truth.

SCENARIO B — PRODUCTION (live engines, ongoing data):
  Feed: Latest sensor readings CSV (engine hasn't failed yet)
  true_RUL here is a RELATIVE proxy (how many cycles since last observation).
  Use model predictions for maintenance alerts (CRITICAL/WARNING/NOMINAL).
  After the engine eventually fails, go back and audit past predictions
  against the known failure date to measure model accuracy retrospectively.

Status thresholds (frontend UI badges):
  CRITICAL : predicted_RUL < 15% of dataset's max RUL
  WARNING  : predicted_RUL < 40% of dataset's max RUL
  NOMINAL  : everything else
  (These are DYNAMIC / relative thresholds — recalculated per uploaded file
   so they work correctly for files with 20 rows AND files with 2000 rows.)

================================================================================
  SECTION 18: CRITICAL TECHNICAL NOTES FOR AI/DEVELOPERS
================================================================================

1. FEATURE COUNT: The trained LightGBM model expects EXACTLY 69 features.
   If you add or remove any feature engineering step, you must RETRAIN the model.

2. ANOMALY_SCORE IS A FEATURE: During training, 'anomaly_score' was kept in X
   (it is NOT in the drop_columns list in trainig_pipeline.py). At inference,
   if the input CSV doesn't have this column, add it as 0.0 (neutral default).
   DO NOT drop it from X before calling model.predict().

3. SCALER MUST INCLUDE ANOMALY_SCORE: The StandardScaler was fit on features
   including 'anomaly_score'. So at inference, add anomaly_score=0.0 BEFORE
   calling scaler.transform(). Then keep it in X for the model.

4. PROXY RUL AT INFERENCE: true_RUL at inference is computed as:
   max_cycle_per_engine - current_cycle within the INPUT FILE ONLY.
   For a 20-row file with cycles 141-160, max_RUL = 19, min_RUL = 0.
   This does NOT mean the engine is dead — it means cycle 160 is the LAST
   cycle in the FILE. In production, the engine may have many more cycles.

5. DYNAMIC STATUS THRESHOLDS: The frontend uses relative thresholds for
   CRITICAL/WARNING/NOMINAL badges:
     CRITICAL = predicted_RUL < 15% of dataset's own max RUL
     WARNING  = predicted_RUL < 40% of dataset's own max RUL
   This prevents all rows from being flagged CRITICAL when a small file
   (e.g., 20 rows with max RUL=16) is uploaded.

6. ENCODING: All file I/O uses encoding='utf-8'. The Flask app sets
   sys.stdout.reconfigure(encoding='utf-8') to prevent Windows charmap errors
   from Unicode characters in logging output.

7. ROLLING FEATURES USE min_periods=1: This allows rolling statistics to be
   computed even on the first row (where window isn't full yet). Essential for
   small input files.

8. RUN FROM PROJECT ROOT: ALL scripts (inference, frontend, training) must be
   run from E:\APU_Predictive_Maintenance\ because all paths in config.yaml
   are relative to the project root.
