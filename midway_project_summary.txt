================================================================================
  SECTION 1: WHAT IS THIS PROJECT?
================================================================================

Full Name : APU Predictive Maintenance System
Goal      : Predict the Remaining Useful Life (RUL) of an Auxiliary Power Unit
            (APU) engine — i.e., how many more operational cycles an engine has
            before it fails — AND detect the type of fault occurring in it.

Why APU?
  An Auxiliary Power Unit is a small engine on aircraft/vehicles used to
  provide power when the main engine is off. Predicting when it will fail
  lets maintenance teams act BEFORE a breakdown happens (Predictive Maintenance
  vs. Reactive Maintenance).

What does the system do (end-to-end)?
  1. Takes raw engine sensor time-series data as input.
  2. Artificially injects fault signatures into the healthy data to create a
     rich training dataset with known fault labels.
  3. Splits the data (train/test) in a way that respects time-series integrity.
  4. Engineers meaningful features from raw sensor readings.
  5. Trains a LightGBM (LGBM) regression model to predict RUL.
  6. Tracks all experiments using MLflow.
  7. Saves the trained model for deployment.

The current model is a REGRESSION model — it predicts the number of cycles
remaining (RUL = Remaining Useful Life). This is more powerful than just 
"is it failing yes/no" because it tells you WHEN.

  SECTION 2: THE DATASET
================================================================================

Source Dataset:
  File   : Artifacts/raw/train_FD002.csv   (also copied to
            Artifacts/training_datasets/train_FD002.csv)
  Origin : NASA CMAPSS (Commercial Modular Aero-Propulsion System Simulation)
           Dataset — specifically the FD002 subset.
  Size   : ~8.8 MB (thousands of engine cycles across 260 engines)

What is in the raw dataset?
  Each row represents ONE operational cycle of ONE engine. The columns are:

  - engine_id     : Unique identifier for each engine unit (1 to 260)
  - cycle         : The cycle number for that engine (starts at 1, goes up
                    until the engine fails — so higher cycle = closer to death)
  - op_setting_1  : Operational setting 1 (flight altitude, load, etc.)
  - op_setting_2  : Operational setting 2
  - op_setting_3  : Operational setting 3
  - sensor_1 to sensor_21 : 21 onboard sensor readings per cycle
                    (e.g., temperature, pressure, rotational speed, vibration)

This raw data represents HEALTHY engines (no faults). The engine simply
degrades naturally until failure. The dataset has NO fault labels by default.


================================================================================
  SECTION 3: FAULT INJECTION (The Most Important Step — What Makes This Unique)
================================================================================

File: NoteBook/Fault_injection/fault_injection.py
      (Module version: src/Data_preprocessing/Fault_injection/fault_injection.py)

Since the NASA dataset only contains healthy engine degradation (no explicit
fault events), we SYNTHETICALLY INJECT faults into the data. This creates a
labeled dataset that the model can learn from.

An Isolation Forest (an unsupervised ML model from scikit-learn) is trained
on the healthy data first. It then scores each data point — healthy readings
get low anomaly scores, faulty readings get high anomaly scores.

5 Fault Types Are Injected:
  -----------------------------------------------------------------------
  Fault | Name            | Affected Sensors | Description
  -----------------------------------------------------------------------
  0     | healthy         | none             | Original unmodified data
  1     | gradual_drift   | sensor_2, sensor_7  | Values slowly drift up/down
                                               over time (max ±10% of mean)
  2     | bias_shift      | sensor_4, sensor_8  | A sudden constant offset
                                               is added from a random cycle
  3     | noise_increase  | sensor_3         | Signal noise grows linearly
                                               from 1x to 3x the original std
  4     | spike           | sensor_9         | Sudden large spikes (3–5x std)
                                               appear randomly (5% density)
  5     | coupled_fault   | sensor_11, sensor_12 | Two sensors drift together
                                               at the same rate (coupled)
  -----------------------------------------------------------------------

Output of Fault Injection:
  File: Artifacts/Fault_injected_data/Fault_injection_dataset.csv

What this output file looks like (columns):
  All original columns (engine_id, cycle, op_setting_1-3, sensor_1 to sensor_21)
  PLUS these new columns added by fault injection:
  - anomaly_score  : Score from IsolationForest (higher = more anomalous)
  - fault_label    : Integer (0=healthy, 1=gradual_drift, 2=bias_shift,
                             3=noise_increase, 4=spike, 5=coupled_fault)
  - fault_type     : String version of fault_label (e.g., "gradual_drift")
  - fault_target   : Which sensors were affected (e.g., "sensor_2|sensor_7")

Size: The output has 6x more rows than the input because each fault type
is applied to EVERY engine in the dataset independently (so 260 engines × 6
variants = 1,560 engine histories).

Integrity Checks Done Automatically:
  - Classes are balanced (equal rows per fault type)
  - No NaN values exist
  - The healthy portion is byte-identical to the original raw data
  - Faulty anomaly scores are higher than healthy scores


================================================================================
  SECTION 4: DATA SPLITTING
================================================================================

Script: entrypoint/data_split.py  →  calls →  src/Data_preprocessing/Data_split/Data_split.py

Input : Artifacts/Fault_injected_data/Fault_injection_dataset.csv
Output: Artifacts/Data_split/Train_datasets/train_dataset.csv
        Artifacts/Data_split/Test_datasets/test_dataset.csv

How it splits:
  - Goes by ENGINE UNIT, not by individual rows. This is critical.
  - 80% of engines go to TRAIN, 20% go to TEST.
  - The order within each engine (cycles) is preserved — NOT shuffled.
  - This prevents DATA LEAKAGE: the model never trains on cycles from
    an engine it will later be tested on.
  - Random seed = 42 for reproducibility.

Why engine-based splitting?
  If you split row-by-row randomly, cycles from the same engine end up
  in both train and test. The model would be "cheating" because it has
  already seen that engine's early cycles. In the real world, the model
  will be deployed on BRAND NEW, UNSEEN engines.


================================================================================
  SECTION 5: FEATURE ENGINEERING
================================================================================

Script: entrypoint/feature_engineering.py  →  calls  →
        src/Pipelines/feature_engineering_pipeline.py (class: FeatureEngineering)

Input : Artifacts/Data_split/Train_datasets/train_dataset.csv
        Artifacts/Data_split/Test_datasets/test_dataset.csv
Output: Artifacts/preprocessed/train_preprocessed/train_preprocessed.csv
        Artifacts/preprocessed/test_preprocessed/test_preprocessed.csv
        Artifacts/Scaler/scaler.pkl  (saved StandardScaler object)

Active Sensor Columns Used (14 informative sensors, others dropped as noise):
  sensor_2, sensor_3, sensor_4, sensor_7, sensor_8, sensor_9,
  sensor_11, sensor_12, sensor_13, sensor_14, sensor_15, sensor_17,
  sensor_20, sensor_21

Features Engineered (4 steps):

  Step 1 — RUL (Remaining Useful Life):
    RUL = max_cycle_of_engine - current_cycle
    Tells the model how many cycles remain before the engine failed.
    This is the TARGET VARIABLE for training.

  Step 2 — Operating Condition Normalization:
    Sensors are grouped by (op_setting_1, op_setting_2, op_setting_3).
    Within each group, sensors are mean-centered.
    WHY: Engines run under different conditions (high altitude vs low),
    which shifts sensor readings. This removes that "operational bias"
    so the model focuses on DEGRADATION, not operating mode.

  Step 3 — Cycle Normalization:
    cycle_normalized = cycle / max_cycle_of_engine
    Converts cycle into a 0–1 value representing % of engine life used.
    WHY: A cycle-50 reading means very different things for an engine
    that lives 100 cycles vs. 400 cycles.

  Step 4 — Rolling Window Features (window=5 cycles):
    For each of the 14 active sensors, 3 new features are created:
    - {sensor}_rolling_mean  : Average of last 5 cycles (smooth trend)
    - {sensor}_rolling_std   : Std dev of last 5 cycles (instability)
    - {sensor}_trend         : Cycle-to-cycle difference (direction)
    WHY: A single cycle reading is noisy. Rolling features give the
    model temporal context — is the sensor stable or deteriorating?

  Step 5 — StandardScaler:
    All numeric features (except engine_id, RUL, fault columns) are
    scaled to mean=0, std=1 using StandardScaler.
    The scaler is FIT on train data ONLY, then applied to test data.
    The scaler object is saved as scaler.pkl for inference.

  SECTION 6: MODEL TRAINING
================================================================================

Script: entrypoint/training.py  →  calls  →
        src/Pipelines/trainig_pipeline.py (class: TrainingPipeline)

Algorithm: LightGBM Regressor (LGBMRegressor)
  LightGBM is a gradient boosting framework by Microsoft. It is extremely
  fast, memory-efficient, and state-of-the-art for tabular data. It builds
  an ensemble of decision trees that correct each other's errors.

Model Hyperparameters (from config/config.yaml):
  - n_estimators     : 400  (number of boosting rounds / trees)
  - learning_rate    : 0.05 (step size per tree — smaller = more careful)
  - max_depth        : -1   (unlimited tree depth, controlled by num_leaves)
  - num_leaves       : 50   (max leaf nodes per tree)
  - subsample        : 1.0  (use all rows per tree)
  - colsample_bytree : 1.0  (use all features per tree)
  - min_child_samples: 20   (min samples needed to create a new leaf)

Input : Artifacts/preprocessed/train_preprocessed/train_preprocessed.csv
        Artifacts/preprocessed/test_preprocessed/test_preprocessed.csv

Features (X): All columns except engine_id, fault_label, fault_type,
              fault_target, and RUL
Target  (Y): RUL (Remaining Useful Life — regression target)

Metrics Evaluated:
  - MSE  (Mean Squared Error)
  - MAE  (Mean Absolute Error)
  - RMSE (Root Mean Squared Error)
  - R²   (R-squared — coefficient of determination, higher is better)

Output: Artifacts/Model/model_LGBM.pkl  (saved trained model ~1.8MB)
